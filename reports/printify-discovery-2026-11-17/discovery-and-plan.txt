OFFICIAL API FINDINGS

Source: https://developers.printify.com/ (reviewed 2026-11-17).
Bearer-token access lists shops and shop-scoped products. Shipping can be quoted
before creating an order. Existing-product orders reference product/variant IDs.
An external_id is unique within a shop; a duplicate returns 409 and the existing
order reference. Webhooks use raw-body HMAC-SHA256 in X-Pfy-Signature.
New shops default to automatic approval after 24 hours: creating an order can
cause production even without calling send_to_production. Verify manual approval
in Printify before any real API test order. Existing-channel functionality is
supported, but suitability of this particular Wix shop remains unverified.

PROPOSED PLAN FOR REVIEW

1. Read-only account and catalog inventory
   Securely provision PRINTIFY_API_TOKEN with the read permissions needed for
   discovery, in ignored server configuration or an approved secret store. Never
   put it in chat, source or reports. Enumerate shops, identify the Wix channel,
   paginate every product and capture product details and catalog/provider data.
   Save restricted raw JSON plus a reviewable CSV mapping of shop/product/variant
   IDs, sizes/colors, enabled state, blueprint/provider, supplier cost/currency,
   images, descriptions, artwork references/placements and shipping information.
   Compare every variant and verify artwork, including embroidery requirements.
   Hold missing or unrecoverable assets for review.

   Decide whether to fulfill through the existing shop or a separate API shop
   after inspecting account capabilities and approval settings. Prefer isolation
   where it protects Wix orders, but do not copy products merely by assumption.
   If copying is needed, review a source-to-target mapping and verify provider,
   artwork, print areas and variants before enabling any copied product. Preserve
   the Wix connection and all original products.

2. Native merchandise catalog and administration
   Add Branded Merchandise within CSA Store with explicit supplier/fulfillment
   identity and provider-neutral supplier records. Decide the additive catalog
   schema after the inventory is reviewed. Keep retail prices and enable/disable
   state local; refresh supplier specifications and availability through a
   reviewable diff without overwriting retail prices. Preserve source and target
   IDs separately. Exclude merchandise from farm inventory, formula pricing,
   Local Line/Square publication and member-credit workflows by explicit type.
   Reuse admin authentication/roles; add explicit merchandise permissions.

3. Checkout, fulfillment and customer status
   Extend existing Stripe utilities and durable payment processing with an
   explicit merchandise order kind. Merchandise mode selection must use the
   existing test client independently of the live primary key. Never switch the
   shared primary credential to test merchandise. Start with checkout disabled,
   supplier order creation disabled and production submission disabled.

   Collect a shipping address before requesting a supplier quote. Freeze the
   address, selected service, variants, retail prices, shipping, tax and expiry
   before Checkout creation. An address change requires a new quote; Stripe must
   not silently accept an unquoted destination. Review shipping destinations,
   retail tax configuration and supplier tax separately. Record order kind and
   fulfillment IDs in Stripe metadata and retain payment/session IDs locally.

   Only verified, attributed successful payment can atomically mark an order paid
   and enqueue fulfillment. A supplier adapter processes a durable outbox with a
   frozen body, stable external reference and stored receipts. Reconcile unknown
   outcomes before any retry; never replace an uncertain operation with a new
   order reference. Production release is a separate controlled step. Persist
   signed provider events, deduplicate delivery and reconcile current supplier
   state before transitions. Add polling recovery, bounded retries, error logs
   without secrets, admin recovery actions and multiple-shipment tracking.
   Reuse authenticated access and secure guest order tokens for customer status.
   Reuse the existing storefront Stripe destinations, signing secrets and
   verified-event route, dispatching merchandise using metadata and persisted
   payment ownership. Configure the existing test destination's missing signing
   secret separately from live. Add a Printify webhook secret during reviewed
   setup; existing turkey live signing configuration stays intact.

4. Mixed farm and merchandise checkout
   Preserve the requested eventual shared checkout, but implement its missing
   farm order/reservation contract before enabling mixed sales. A parent customer
   order should own payment and allocation records, with independent farm and
   supplier fulfillment children. Review how farm stock is reserved and orders
   are handed to existing pickup/delivery operations; do not insert fake sales
   into Local Line mirror tables. Merchandise shipping is charged independently
   of farm delivery eligibility. A supplier failure must leave farm fulfillment
   operable. Recommend merchandise-only validation first, then mixed checkout
   validation as a distinct release gate. This does not remove mixed checkout
   from the requested deliverables.

5. Administration, reporting and refunds
   Show variant availability, local retail, timestamped supplier costs, payment,
   production, shipment/tracking and errors. Retain gross item sales, discounts,
   shipping charged, tax, supplier production/shipping costs, refunds and actual
   Stripe fees from balance transactions. Allocate shared fees consistently and
   label profit estimates until actual costs are known. Keep merchandise revenue
   identifiable by order/line kind. Cancellation and refund are separate reviewed
   operations: a payment refund never proves supplier cancellation. Preserve
   uncertain receipts and expose recovery without duplicating fulfillment.
